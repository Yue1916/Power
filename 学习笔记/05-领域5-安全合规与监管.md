### 🌱 一句话入门（零基础先看这里）

保护 AI 系统 = **谁负责什么（责任共担）+ 谁能访问什么（IAM）+ 数据怎么保护（加密）+ 怎么防攻击 + 怎么留痕追踪**。

- **责任共担**：AWS 管"云本身"（机房/硬件/网络），你管"云里的东西"（数据、访问、配置）。
- **IAM**：管"谁能对哪些资源做什么"；最佳实践是**最小权限**、用**角色（临时凭证）**、开 **MFA**、别用根用户。
- **加密**：静态 + 传输中都加密；用 **KMS** 管密钥。
- **AI 特有攻击**：数据投毒、对抗性输入、模型反演、提示词注入。
- **留痕追踪**：CloudTrail 记 API 调用、Model Cards/Lineage 记模型来源。

> 记忆：**责任共担 → IAM 最小权限 → 加密(KMS) → 防 AI 攻击 → 监控+溯源**。

> **第 1 课：责任共担模型 + IAM 基础 + 根用户/MFA**

#### 1. AWS 责任共担模型 (Shared Responsibility Model)（高频）

- **AWS 负责"云本身的安全 (security OF the cloud)"**：全球基础设施——区域、可用区、数据中心物理安全；运行服务的硬件、主机操作系统、虚拟化层、网络组件。
- **客户负责"云内部的安全 (security IN the cloud)"**：安全地使用服务——限制访问、加密、遵循最佳实践、正确配置服务和应用、保护数据。
- **责任级别取决于服务**：
  - 在 **EC2** 上部署模型 → 你还要管实例操作系统、安全补丁、扩展、应用安全（责任更多）。
  - 用 **SageMaker 无服务器推理** → AWS 管所有底层基础设施，你几乎不用管（责任更少）。

#### 2. IAM（身份和访问管理）基础

- **IAM**：管理 AWS 账户/资源的**安全访问**；创建管理用户、授予权限；通过 **IAM 权限策略**决定用户能对资源做什么。
- 特点：**全球资源**（不限区域，但可限制用户对特定区域的权限）、与 AWS 服务集成、支持 **MFA**、支持**身份联合 (federation)**、**本身免费**（只为使用的其他服务付费）。

#### 3. 根用户 (Root User) 与 MFA

- **根用户**：创建账户时的初始身份，对所有服务资源有**完全访问权、无法限制**；用注册邮箱+密码登录。
- 保护根用户：设强密码、**启用 MFA**、绝不共享密码/访问密钥、删除根用户访问密钥。
- **最佳实践：不用根用户做日常任务**（除极少数如账单管理）→ 创建 **IAM 用户**并赋管理权限来日常使用。
- **单因素 vs 多因素**：只用用户名+密码=单因素（有风险）；**MFA** 需额外的物理/虚拟设备生成的编号，即使密码泄露也进不去。建议创建账户后**立即启用 MFA**。

#### 4. IAM 用户

- 代表与 AWS 交互的人，含名称和凭证；**最佳实践：为每个人建独立 IAM 用户**、不共享凭证（否则无法追溯谁做了什么）。
- 默认**无任何权限**，需显式授予。

> **第 2 课：IAM 策略、组、角色**

#### 1. IAM 策略 (Policy)

- **JSON 文档**，允许或拒绝用户对服务/资源的权限。
- **最小权限原则 (Least Privilege)**：只授予完成任务所需的权限。

#### 2. IAM 组 (Group)

- IAM 用户的集合；给组分配策略 → 组内所有用户获得该权限。按**工作职能**组织（开发组/QA 组/管理员组）。
- 规则：**一个组可多个用户、一个用户可属多个组、组不能嵌套（组不能属于其他组）**。
- 最佳实践：**策略附加到组**，仅给用户附加其独有的额外权限。

#### 3. IAM 角色 (Role)（重点）

- 个人或 **AWS 服务**可**代入 (assume)** 的身份，获得对其他资源的**临时访问凭证（自动过期）**——比长期凭证更安全。
- 每个角色有**信任策略 (trust policy)** 决定谁能代入。
- 场景：避免把长期凭证硬编码进代码（泄露风险）。

#### 4. 基于身份 vs 基于资源的策略

- **基于身份的策略 (Identity-based)**：附加到用户/组/角色。
- **基于资源的策略 (Resource-based)**：附加到资源（如 S3 存储桶策略）。
- **权限合并规则**：最终权限是两者之和；任一策略**允许**即允许；**任一策略的显式拒绝 (explicit deny) 覆盖一切允许**。

> **第 3 课：身份联合、CloudTrail、S3 阻止公共访问、SageMaker Role Manager**

#### 1. 身份联合 (Identity Federation) 与 IAM Identity Center

- **身份联合**：用户通过外部身份提供商（如 Active Directory）认证，获得 AWS 的**临时凭证**。
- **AWS IAM Identity Center**：用外部 IdP 或内建目录认证；用户称**员工身份**；登录后通过门户访问控制台或获取临时密钥。
- 优势：**多账户企业**无需在每个账户管 IAM 用户，可在**中央存储库**管理所有账户权限、按组分配权限集；用**角色**授临时权限。**AWS 建议用 IAM Identity Center 管理用户（而非 IAM 用户）**。

#### 2. AWS CloudTrail（审计）

- 捕获账户的 **API 调用和相关事件**，把日志投递到指定 **S3 存储桶**。
- 与 SageMaker 集成：**捕获所有 SageMaker API 调用（除 InvokeEndpoint 调用终端节点外）**；可查请求者、IP、时间等，用于**审计和验证安全配置**。

#### 3. Amazon S3 阻止公共访问 (Block Public Access)

- 在**存储桶或账户级别**阻止对象的公共访问；**账户级启用**后所有现有/新存储桶都不能授予公共访问；**覆盖**存储桶策略或 ACL 授予的公共权限。

#### 4. SageMaker Role Manager

- 简化 IAM 角色创建，无需自己写权限策略；为 12 项 ML 活动提供**三种预配置角色**：
  - **数据科学家 (Data Scientist)**：一般 ML 开发和实验。
  - **MLOps**：管理模型/管道/实验/终端节点，但**无需访问 S3 数据**。
  - **SageMaker 计算 (Compute)**：给计算资源用来跑训练和推理。

> **第 4 课：加密、KMS、Macie、VPC/PrivateLink**

#### 1. 加密（静态 + 传输中）

- **所有 AWS 服务都能加密静态数据和传输中数据**。加密后即使有人访问存储卷也读不了（需密钥才能解密）。
- **客户端加密**：发送到 AWS 前自己加密；**服务器端加密**：由 AWS 服务加密（最简单，配置时启用）。
- **默认加密的服务**：**Amazon S3、DynamoDB、SageMaker** 默认加密数据（SageMaker 加密 ML 存储卷上所有数据）——用服务自有密钥。

#### 2. AWS KMS（密钥管理服务）

- 在账户中**创建、管理、使用加密密钥**；用 IAM 策略控制**谁能用密钥** → 多一层保护（即使误获 S3 读权限，无 KMS 密钥也读不了数据）。
- **客户管理的密钥 (customer managed key)**：可控密钥策略、IAM 策略、**轮换策略**、启用/禁用。
- **传输中加密**：所有 AWS 服务终端节点支持 **TLS/HTTPS**；SageMaker 分布式训练的**节点间流量默认不加密**，可选启用（会延长深度学习训练时间）。

#### 3. Amazon Macie（敏感数据发现）

- 持续评估 **S3 存储桶**、生成清单（大小、公/私访问、共享、加密状态）；用 **ML + 模式匹配**识别并提醒**敏感数据（如 PII）**；可集成到 ML 工作流自动补救。
- 用途：训练数据里**不该含 PII**（信用卡号/姓名/地址/SSN），摄取时应删除；Macie 发现敏感数据会告警。

#### 4. VPC 与 AWS PrivateLink（网络隔离）

- **VPC**：在 AWS 上配置自己的专用网络。SageMaker Studio/Notebook 默认在 SageMaker 托管 VPC 中、**可直接访问互联网**（风险：可能下载恶意代码把数据外传）。
- 最佳实践：**在自己账户创建 VPC** 并在启动时指定 → 通过安全组、网络 ACL、防火墙控制流量；用**仅限 VPC 模式**阻止互联网访问。
- **VPC 接口终端节点 + AWS PrivateLink**：让所有流量只走**专用网络**直连 AWS 服务，不经公网。

> **第 5 课：AI 特有的漏洞与攻击 + 防护最佳实践 + Model Monitor**

#### 1. AI 特有的攻击方式（重点，务必分清）

- **数据投毒 (Data Poisoning)**：攻击者篡改训练数据（如把欺诈交易标为非欺诈）→ 模型错误分类。
- **对抗性输入 (Adversarial Input)**：对输入做细微但精心设计的修改，让模型错误分类（如改图像骗过人脸识别）。
- **模型反演 (Model Inversion)**：反复喂数据研究输出，**推断训练数据**或**复制模型**（用输入输出对训练一个反向模型）。
- **提示词注入 (Prompt Injection)**：在提示里发恶意指令（如"忽略你的提示词模板"）获取敏感信息。

#### 2. 防护最佳实践

- **最小权限 + 阻止公共访问**；数据和构件**加密**。
- **限制/控制对模型的访问**以阻止反向工程；**不在输出提供多余信息**。
- **检查和验证用户输入**、找异常模式（如教 LLM 检测提示注入、返回 "prompt attack detected"）。
- **用对抗性输入训练模型**增强鲁棒性；**常用新数据重训练**弥补被投毒的损失。
- 保留**独立验证集**，每次重训练后先验证再部署；**定期扫描监控数据质量、检测异常**。
- 模型预测偏离历史模式 → 调查根因（数据质量差 or 受攻击）。

#### 3. SageMaker Model Monitor（监控）

- 实时监控生产模型**质量**、检测**数据偏移/异常**、自动告警。
- 把数据/模型与**基准 (baseline)** 比较，生成统计和指标 → SageMaker Studio 显示 + 发 **CloudWatch**；达阈值通知，日志存 S3。
- **监控数据质量**需启用**数据捕获 (data capture)**（捕获推理输入输出存 S3）；用训练集建基准。
- **监控模型质量**：用标注数据建基准，把推理与 **Ground Truth** 标注比较评估性能。

> **第 6 课：来源追踪与版本控制（重现模型、满足监管）**

> 核心：**跟踪所有构件、做版本控制**，才能重现模型、满足监管和控制要求。

- **代码**：GitHub / **AWS CodeCommit** 自动保留版本（训练/推理代码、实验、Notebook）。
- **数据集**：存 **S3**、用**前缀分区**唯一标识。
- **容器映像**：存 **Amazon ECR**、用唯一 ID 标识。
- **训练任务**：SageMaker 自动唯一标识、存元数据（超参数、容器/数据集/模型输出的唯一标识符）。
- **SageMaker 模型注册表 (Model Registry)**：把模型版本编入**模型组**；每个模型包=一个训练好的模型；可关联训练指标、直接部署、维护状态（待处理/已批准/已拒绝）。
- **SageMaker Model Cards**：记录/检索/共享模型从构思到部署的信息；创建**不可变的**预期用途、风险评级、训练详情、评估结果记录；可导出 PDF 共享。
- **SageMaker ML Lineage Tracking（谱系追踪）**：自动为端到端 ML 工作流各元素创建**图形表示**；用于**模型监管、重现工作流、保留历史**；可查询谱系（如"用了某数据集的所有模型"）。
- **SageMaker Feature Store**：特征集中存储、复用；可查特征组**谱系**、支持**时间点查询 (point-in-time)** 检索特征历史状态。
- **SageMaker 模型控制面板 (Model Dashboard)**：集中门户，查看/搜索账户所有模型；汇总 Model Monitor、Model Cards 信息；可视化谱系、跟踪终端节点性能、找违反数据质量/模型质量/偏差/可解释性阈值的模型。

### ⚠️ 视频未覆盖 / 需补充（对照考纲）

- **Amazon Bedrock AgentCore 身份 (Identity) 与策略 (Policies)**：为 Bedrock 上的 AI **智能体**提供身份认证和访问控制——控制智能体能代表谁、访问哪些工具/资源（智能体安全）。

#### 📎 补充资料（额外阅读）：GenAI 安全范围矩阵 + 各范围安全控制 + MITRE ATLAS

> 来源：AWS "Securing Generative AI: Applying relevant security controls" 整理。范围矩阵在 5.2 也会用到，这里聚焦**安全控制**。

**五个范围与"谁控制什么"**
- **范围 1 消费者应用**：员工用面向消费者的应用（无企业协议，同个人用户条款）。你只控制**自己的数据**。
- **范围 2 企业应用**：组织级采购、有**企业协议**（数据流与范围 1 相同）。你只控制自己的数据，其余靠提供商控制。
- **范围 3 预训练模型**：用预训练 FM（如 Bedrock）自建应用。你控制**应用 + 客户数据**，提供商控制预训练模型。
- **范围 4 微调模型**：用你的数据微调 FM。你**额外控制微调数据和微调模型**。
- **范围 5 自训练模型**：从零训练 FM。你**控制整个范围**、承担所有提供商责任（数据收集/清洗/内容过滤/负责任 AI）。

**各范围的关键安全控制**
- **范围 1/2（用第三方应用）**：
  - **网络控制**（web 代理、出口防火墙 AWS Network Firewall、DLP、CASB）+ **主机控制**（EDR 端点）——但都非万无一失（用户可绕过）。
  - **用户培训**（MITRE ATLAS **AML.M0018**）；强化数据分类与处理策略。
  - 范围 2 额外：审查提供商协议（**你的数据是否用于训练？能否 opt-out？IP 归属？是否赔付第三方侵权？**）；可能有应用内置 **RBAC**。
- **范围 3/4/5（自建应用）**：标准应用安全 + AI 特有控制——
  - **身份和访问控制优先**（OpenID Connect/OAuth 2、MFA）。
  - **RAG 要传播用户身份**到知识库，只返回用户有权访问的数据；**敏感字段在检索阶段就 redact，别指望靠提示词让模型别说**（模型拿不到就不会泄露）。
  - **代理 (Agents) 要把用户身份传播到每个被调用的 API**、逐个授权 → 即使提示注入成功，未授权的操作也会失败。
  - **用 IAM 限制对推理端点的直接访问**（`bedrock:InvokeModel`、`sagemaker:InvokeEndpoint`）——像数据库一样，只允许应用调用、不让用户直连。
  - **WAF** 防传统威胁（SQL 注入、请求洪泛/限流控成本）；**但 WAF 挡不住提示注入**（提示注入是自然语言）。
  - **威胁模型应假设提示注入会成功**，靠**逐个 API 授权**限制其影响。
  - **自托管模型**额外：验证模型构件来源与完整性（代码签名 M0013/验证构件 M0014）、扫描漏洞（M0016）。
  - **内容过滤**：提供商在训练/推理时过滤毒性；你可用 **Bedrock Guardrails** 加额外防护。
  - 范围 4/5 额外：**微调/训练数据要精选**（M0007），FM **无法选择性删除单条训练记录**（要删得重新微调）——慎用 PII（"被遗忘权"）；**加密自定义模型构件**（可用**客户管理的 KMS 密钥**，调用需 `InvokeModel` + KMS `Decrypt` 权限）。
- **MITRE ATLAS**：一个 AI 威胁与缓解的知识库（缓解 ID 形如 **AML.Mxxxx**）；其他参考：**OWASP AI Security & Privacy Guide**、**NIST AI RMF**。

**责任共担与 IAM**
- **责任共担模型 (Shared Responsibility Model)**：AWS 管"云本身"、客户管"云内部"。
- **IAM**：管理谁能对资源做什么；全球资源、免费、支持 MFA/联合。
- **根用户 (Root User)**：完全权限、不可限制；日常别用、开 MFA。
- **MFA（多重身份验证）**：额外设备编号，防密码泄露。
- **最小权限原则 (Least Privilege)**。
- **IAM 用户 / 组 (Group) / 角色 (Role)**：组不能嵌套；角色给**临时凭证**、更安全。
- **基于身份 / 基于资源的策略**；**显式拒绝覆盖允许**。
- **IAM Identity Center**：中央管理多账户用户（推荐替代 IAM 用户）；**身份联合 (Federation)**。

**加密与网络**
- **静态加密 / 传输中加密 (at rest / in transit)**；**TLS/HTTPS**。
- **客户端 / 服务器端加密**；S3/DynamoDB/SageMaker **默认加密**。
- **AWS KMS**：创建/管理密钥、控制谁能用、密钥轮换。
- **VPC / VPC 接口终端节点 / AWS PrivateLink**：网络隔离、走专用网络。
- **S3 阻止公共访问 (Block Public Access)**。

**AI 攻击**
- **数据投毒 (Data Poisoning) / 对抗性输入 (Adversarial Input) / 模型反演 (Model Inversion) / 提示词注入 (Prompt Injection)**。

**监控与溯源**
- **AWS CloudTrail**：记录 API 调用（审计）。
- **Amazon Macie**：发现 S3 中的敏感数据 (PII)。
- **SageMaker Model Monitor**：监控漂移/质量（需数据捕获）。
- **SageMaker Model Registry / Model Cards / ML Lineage Tracking / Feature Store / Model Dashboard**：版本控制与来源追踪。
- **SageMaker Role Manager**：预配置 ML 角色（数据科学家/MLOps/计算）。

### 易考点 / 陷阱

- **责任共担**（最高频）：**AWS 管"云本身"（OF the cloud）、客户管"云内部"（IN the cloud）**；服务越托管（如 SageMaker 无服务器）客户责任越少，越接近底层（如 EC2）客户责任越多。
- **IAM 三件套**：用户（人）、组（按职能、不能嵌套、策略附组）、**角色（临时凭证、给服务/联合用、更安全）**。
- **策略合并**：允许相加，**显式拒绝永远覆盖允许**。
- **优先用角色/临时凭证、IAM Identity Center**，别硬编码长期凭证、别用根用户日常操作、**立即开 MFA**。
- **加密**：静态 + 传输中；**KMS 管密钥**（即使拿到 S3 读权限，无 KMS 密钥也读不了）；S3/DynamoDB/SageMaker 默认加密。
- **Macie=发现 PII**；**CloudTrail=记录 API 调用审计**；别混。
- **四种 AI 攻击对号入座**：改训练数据→投毒；改输入骗模型→对抗性输入；靠输出推训练数据/复制模型→模型反演；提示里塞恶意指令→提示注入。
- **来源追踪工具**：**Model Cards**（不可变文档）、**ML Lineage Tracking**（工作流图/谱系）、**Model Registry**（版本+状态）、**Feature Store**（特征+时间点查询）。
- **网络隔离**：VPC + **PrivateLink/VPC 接口终端节点**让流量不经公网。
- **Model Monitor** 监控数据质量需先开**数据捕获**。

### 🎴 闪卡 Q&A（遮住答案自测）

<details><summary>1. 责任共担模型里，AWS 和客户各负责什么？</summary>
AWS 负责"云本身的安全"（基础设施/硬件/网络/物理）；客户负责"云内部的安全"（数据、访问控制、加密、正确配置）。</details>

<details><summary>2. IAM 用户、组、角色的区别？角色的优势？</summary>
用户=代表人的身份；组=按职能的用户集合（策略附组、不能嵌套）；角色=可被代入、给<strong>临时凭证</strong>，比长期凭证更安全。</details>

<details><summary>3. 基于身份和基于资源的策略如何合并？</summary>
最终权限是两者之和，任一允许即允许；但<strong>任一策略的显式拒绝覆盖所有允许</strong>。</details>

<details><summary>4. 为什么推荐用 IAM 角色和 IAM Identity Center 而非长期凭证/IAM 用户？</summary>
角色给自动过期的临时凭证、更安全；Identity Center 可集中管理多账户用户、支持身份联合，避免在每个账户管 IAM 用户。</details>

<details><summary>5. AWS KMS 的作用？为什么加密还要控制密钥访问？</summary>
KMS 创建/管理加密密钥并用 IAM 控制谁能用密钥。即使有人误获 S3 读权限，没有 KMS 密钥也无法解密数据，多一层保护。</details>

<details><summary>6. Amazon Macie 和 AWS CloudTrail 分别做什么？</summary>
Macie 发现 S3 中的敏感数据（如 PII）；CloudTrail 记录账户的 API 调用用于审计。</details>

<details><summary>7. 四种 AI 特有攻击分别是什么？</summary>
数据投毒（篡改训练数据）、对抗性输入（改输入骗模型）、模型反演（靠输出推训练数据/复制模型）、提示词注入（提示里塞恶意指令）。</details>

<details><summary>8. 怎么让 AI 流量不经过公网访问 AWS 服务？</summary>
在自己 VPC 中用 VPC 接口终端节点 + AWS PrivateLink，让流量走专用网络。</details>

<details><summary>9. 哪些 SageMaker 功能用于模型的来源追踪和版本控制？</summary>
Model Registry（版本+状态）、Model Cards（不可变文档）、ML Lineage Tracking（工作流谱系图）、Feature Store（特征+时间点查询）、Model Dashboard（集中查看）。</details>

<details><summary>10. 用 SageMaker Model Monitor 监控数据质量的前提是什么？</summary>
必须启用数据捕获 (data capture) 来捕获推理输入输出并存 S3，再用训练集建基准做比较。</details>

> **第 2 课：AI 合规标准与法规 + NIST 风险估算 + 算法问责法案**

#### 1. AI 相关标准与法规

- **ISO 42001 / ISO 23894**（2023 发布）：建立**评估和管理 AI 系统风险**的机制/框架，鼓励负责任 AI 实践、促进全球互操作性。**标准是强烈建议但非法律**。
- **欧盟 AI 法案 (EU AI Act)**：全球首个主要监管机构提出的**全面 AI 法规**，按风险**三级**分类：
  - **不可接受风险**：彻底**禁止**（如社交评分、抓取面部图像建库、推断职场/教育情绪）。
  - **高风险**：需遵守特定法律要求（如简历排名工具）——需风险管理系统、数据监管、记录合规。**大多数 AI 属高风险**。
  - **未禁止/非高风险**：基本不受监管。
- **GDPR（通用数据保护条例）**：欧盟法规，常被当作**全球标准**，即使不面向欧盟公民也应关注。
- **NIST AI RMF（AI 风险管理框架）**：**自愿性**框架，四个功能：**监管 (Govern)、映射 (Map)、测量 (Measure)、管理 (Manage)**。

#### 2. 风险估算（NIST RMF）

- **风险 = 事件发生的可能性 × 后果严重程度**（风险矩阵）。
- 步骤：确定 AI 用例和利益攸关方 → 识别潜在有害事件、用风险矩阵定级 → 用安全控制和监控缓解**固有风险 (inherent risk)** → 剩下的是**剩余风险 (residual risk)** → 汇总各风险，按**最高的剩余风险**确定系统总体评级。

#### 3. 算法问责法案 (Algorithmic Accountability Act)

- 美国拟议法案：要求公司**评估其 AI 系统的影响**、确立透明度、支持消费者知情选择。
- 两大目标：①**透明度**（如消费者有权知道贷款为何被拒）②**消除偏差**（结果不受种族/性别/宗教/政治/城乡等属性不当影响）→ 需**测试和监控**模型结果与训练数据的偏差（用 **SageMaker Clarify**）。

---

> **第 3 课：合规工具（Audit Manager / Guardrails / Config / Inspector / Trusted Advisor）**

- **AWS Audit Manager**：把**合规要求映射到 AWS 使用数据**，自动收集合规/不合规**证据**、生成**评估报告**给审计员；有内置框架（含**生成式 AI 最佳实践**、SOC 2），也可自定义框架。
- **Amazon Bedrock Guardrails**：按用例和负责任 AI 策略实施防护——可配置阈值过滤仇恨/侮辱/色情/暴力，用自然语言**定义要避免的主题**、**检测并屏蔽/编辑 PII**，对提示和响应都能设，并可配置被屏蔽时的两条自定义响应。
- **AWS Config**：提供 AWS 资源当前配置的详细清单，**资源配置一变就记录快照**；用**配置规则**评估，不合规可用 **Systems Manager Automation** 自动补救；**一致性包 (Conformance Packs)** 打包规则+补救（有 AI/ML 运营最佳实践、SageMaker 安全最佳实践包）。**Config 在资源级别监控**。
- **Amazon Inspector**：在**应用程序级别**检查应用和容器的**安全漏洞**（如 EC2 开放访问、易受攻击的软件版本），自动跑评估、给按严重性排序的调查结果和修复建议。
- **AWS Trusted Advisor**：按最佳实践持续评估环境（成本优化、性能、弹性、安全、卓越运营、服务限制），建议纠正偏差。

> 对号入座：**资源配置合规→Config；应用漏洞→Inspector；生成审计报告→Audit Manager；最佳实践检查→Trusted Advisor；合规报告下载→Artifact**。

---

> **第 4 课：数据治理（策管、发现/编目、保护）+ 角色 + DataBrew**

- **数据治理 (Data Governance)**：管理数据的可用性、易用性、完整性、安全性，涉及**人员、流程、技术**。三大部分：**策管 (Curate)、发现与理解 (Discover & Understand)、保护 (Protect)**。
- **关键角色**：
  - **数据拥有者 (Data Owner)**：制定数据策略（治理/合规）的高管，决定谁能访问什么。
  - **数据管理员 (Data Steward)**：懂数据细节、参与日常项目，发现数据问题。
  - **IT**：管理和部署数据治理工具、提供功能。
- **概念**：**数据剖析 (Data Profiling)**（系统检查数据找问题、了解特征）、**数据目录 (Data Catalog)**（让需要的人能找到数据）、**数据谱系 (Data Lineage)**（数据来源、如何移动/转换/存储）。
- **AWS Glue DataBrew**：可视化、无代码数据准备；两个治理功能——**数据剖析**（跑剖析任务建数据配置文件、定义质量规则）+ **数据谱系**（可视化数据从源头的流动）。

---

> **第 5 课：数据质量/集成/安全/生命周期 + Glue Catalog / Data Quality / Lake Formation / S3 存储类**

- **数据质量管理**：找质量问题的**根源**，涉及来源时提醒数据管理员纠正。
- **数据集成 / 主数据管理 (MDM)**：合并多源数据、协调通用数据（如纠正邮箱/姓名拼写），数据管理员定义协调规则和层次。
- **AWS Glue Data Catalog**：存数据来源的**元数据**（位置、架构、数据类型、表定义）；可手动或用**爬网程序**自动填充。
- **AWS Glue Data Quality**：评估 Glue Data Catalog 中的对象；为非编码人员提供设置数据质量规则的简单方式，**推荐规则 + 用 ML 自动检测异常**；跑任务后看哪些规则通过/未通过。
- **数据安全 / 合规 / 生命周期**：基于角色的临时访问（数据管理员在拥有者策略指导下启用）；合规需数据拥有者与安全/法律团队合作；数据治理是**控制与访问的平衡**（控制过多→数据孤岛，控制不足→风险）。
- **AWS Lake Formation**：管理 S3 数据湖的**精细访问控制**（列/行/单元格级），用 Glue Data Catalog 编目；打破数据孤岛、合并结构化/非结构化数据；分析引擎（Athena/Glue/EMR/Redshift）访问前，Glue Data Catalog 先检查 Lake Formation 权限。
- **Amazon S3 存储类（合规留存/成本优化）**：
  - **S3 Standard**：频繁访问。
  - **S3 Standard-IA / One Zone-IA**：不常访问但需快速取回（存储便宜、检索贵）。
  - **S3 Intelligent-Tiering**：访问模式未知/变化，自动分层。
  - **S3 Glacier 系列**：很少访问，**长期归档、数据留存/合规**（不同 Glacier 类检索速度不同）。
  - **生命周期规则 (Lifecycle Rules)**：按天数自动转移到低频/归档层或删除（如 5 天转 IA、120 天转 Glacier Deep Archive、5 年删除）。

> **第 6 课：实施 AI 监管策略 + 生成式 AI 安全范围矩阵**

#### 1. 生成式 AI 安全范围矩阵 (Generative AI Security Scoping Matrix)（重点）

- 责任随使用/实施 AI 的方式**从范围 1 到 5 递增**：
  - **范围 1、2**：用**第三方**消费者/企业应用 → **责任最小**。
  - **范围 3、4、5**：**构建自己的** AI 解决方案，数据用于训练/微调/输出 → 你负责数据和模型的**风险分类、威胁建模、限制访问、安全控制、终端节点弹性**。
- 监管/合规责任随范围扩大而增加。
- **主任务：从左到右找解决方案，尽量缩小范围以减少责任**：
  1. 先用**全训练 AI 服务**（如 Comprehend、Translate）；
  2. 不够再用**预训练模型**（如 Bedrock，可用 RAG 增强）；
  3. 再考虑**可微调的预训练模型**（如 SageMaker JumpStart）。

#### 2. 实施 AI 监管策略的步骤

- **确定责任范围**：监管合规、法律隐私、风险管理、安全控制、模型弹性。
- **记录 AI 监管策略并培训员工**（责任依工作角色和访问权限而定）：制定**数据治理、访问请求、模型透明度标准**；用所需的合规/认证提供指导。
- **定义监控机制**：监控 AI 系统的性能、合规、偏差，按预定义阈值行动。
- **经常审查结果、按需修改策略**，保持与业务目标和 AI 安全一致。

#### 📎 补充资料（额外阅读）：风险评估层级 + 数据治理风格 + GenAI 数据治理

> 来源：AWS "Learn how to assess the risk of AI systems" / "What is Data Governance" / "Data governance in the age of GenAI" / "ISO 42001" 整理。

**AI 风险的三个层级**
- **模型风险 (Model Risk)**：ML 模型本身的脆弱性和不确定性。
- **AI 系统风险 (AI System Risk)**：AI 系统实现和运营的影响（本文重点）。
- **企业风险 (Enterprise Risk)**：组织整体的财务/运营/战略风险。
- 三层应对齐考虑。风险是**"不确定性对目标的影响"**，非"潜在危害"本身。
- **固有风险 (Inherent)** = 无缓解时的风险；**剩余风险 (Residual)** = 缓解后剩下的；风险评估是**以人为中心、需全组织参与**的活动（含产品/工程/科学/销售/安全团队）。
- 相关标准/法规都要求风险评估：**ISO 42001、ISO 23894、NIST RMF、欧盟 AI 法案**。

**ISO 42001 补充**：2023 年发布的**国际管理体系标准**，为组织**系统性管理 AI 风险**提供指南、鼓励负责任 AI、促进全球互操作性；符合它是展示负责任开发部署 AI 承诺的方式之一。

**数据治理的三种风格（考点）**
- **集中式 (Centralized)**：中央组织负责使命/策略/工具选择，日常操作下放到业务线。
- **联邦式 (Federated)**：各业务单元按需运作，小型中央团队解决重复性问题（如企业级数据质量工具）。
- **自助/去中心 (Self-serve / Decentralized)**：各部门按项目需要做、同时对齐中央策略（如 data mesh）。
- 通常是三者混合，依业务需求平衡**集中与分散**。

**数据治理的核心 = 平衡访问与控制**：控制过多→数据孤岛、扼杀创新；控制不足→数据失控、风险上升。

**GenAI 时代的数据治理（新增关注点）**
- LLM 用例常需**非结构化数据**（文档/转录/图像）+ 结构化数据；非结构化数据要同等严格治理。
- 用户交互次数多 → **数据安全、隐私、访问控制要嵌入用户工作流**。
- 关键步骤：**PII 脱敏/编辑（用 Amazon Comprehend）**、实体识别与链接（AWS Entity Resolution）、数据质量（Glue Data Quality、shift-left 左移尽早查质量）。
- **向量库治理**：嵌入常含敏感数据 → **静态加密（KMS）** + **RBAC/细粒度访问控制**（OpenSearch Serverless、Kendra、Aurora，配合 IAM/Cognito）。
- **用户请求-响应流程的治理**：入口校验提示（合规/毒性，用 Comprehend 或 Bedrock Guardrails）→ 按角色应用 FGAC/RBAC（用 Lake Formation 过滤）→ 对响应做 PII/内容编辑。
- **AI 治理 = 沿用数据治理 + 扩展到特征存储和 ML 模型**（含 FMOps、GenAI 毒性/偏差治理）。

### 易考点 / 陷阱

- **合规工具对号入座（最高频）**：**Artifact**=下载合规报告；**Audit Manager**=生成审计报告/收证据；**Config**=资源配置合规；**Inspector**=应用漏洞；**Trusted Advisor**=最佳实践检查。
- **Config（资源级）vs Inspector（应用级）** 别混。
- **标准 vs 法律**：ISO/SOC 是**建议性标准**（非法律）；**欧盟 AI 法案**是**法规**（按风险三级：禁止/高风险/低风险，多数属高风险）；**NIST AI RMF 是自愿框架**（四功能 Govern/Map/Measure/Manage）。
- **风险 = 可能性 × 严重程度**；固有风险→缓解→剩余风险；按**最高剩余风险**定总体评级。
- **数据治理三部分**（策管/发现理解/保护）+ **三角色**（拥有者定策略、管理员干日常、IT 给工具）。
- **数据谱系 (Lineage)** = 数据来源与流转；**数据目录 (Catalog)** = 让人找到数据；**剖析 (Profiling)** = 查数据质量。
- **Lake Formation = 数据湖精细权限（列/行/单元格）**；**S3 Glacier + 生命周期规则 = 合规留存/归档/自动转层**。
- **生成式 AI 安全范围矩阵**：范围 1-2 用第三方（责任小）、3-5 自建（责任大）；**尽量缩小范围以减少合规责任**；选型从左到右（全训练服务→预训练→可微调）。
- **监管落地四步**：定范围 → 记策略+培训 → 定监控机制 → 定期审查修订。
