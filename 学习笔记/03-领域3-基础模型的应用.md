## 领域概述（学习地图）

领域 3 承接领域 2，聚焦**怎么把基础模型 (FM) 用起来**。回顾：FM 是预训练好、可随时用的大型深度学习模型，用海量数据训练，作为开发起点更快更省。

- **FM 的独特之处**：**适应性**——同一个模型靠输入提示词就能高准确地做多种任务（NLP、问答、图像分类等）；而传统 ML 模型只做**特定单一任务**。

### 🌱 一句话入门（零基础先看这里）

设计一个用基础模型的应用，要想清楚四件事：**选哪个模型、怎么调它的输出、缺知识怎么补、要不要让它自己干活**。

- **选模型**：在成本、延迟、模态、多语言、规模/复杂度、可解释性之间权衡——没有"最好"，只有"最适合你需求的"。
- **调输出**：用**推理参数**（温度、Top K/Top P、长度、停止序列）控制回答的随机性、多样性、长度。
- **补知识**：模型不知道你公司的私有/最新数据 → 用 **RAG**（从向量数据库检索相关内容，拼进提示词），减少幻觉。
- **让它干活**：模型只会"说"，不会"做"（订机票、下采购单）→ 用 **AI 代理 (Agent)**，让它调用 API、执行多步骤任务。

> 四个关键词：**选型权衡 · 推理参数 · RAG · 代理**。

> **第 1 课：选择预训练模型的标准（成本/延迟/模态/复杂度）**

#### 1. 预训练模型的注意事项

- 优势多，但**体积庞大、训练和推理需大量算力** → 对算力有限的个人/组织是挑战。
- 选之前先确认**与需求对齐**：本课重点看**成本、延迟、模态**。

#### 2. 成本 (Cost)

- 训练**时长和成本**是重要考量（硬件、存储费用可能很高）。
- 经典权衡：**准确率 98% 但训练花数十万美元** vs **准确率 97% 但只花几千美元**——**视需求而定**，要在训练时间、成本、性能之间**找平衡**。
- 目标：设计**可扩展、高效、又不牺牲性能**的方案。模型越复杂，对整个生命周期成本影响越大。

#### 3. 延迟 (Latency) 与推理速度

- 若应用需**实时**处理并给结果，选模型时必须考虑延迟；复杂模型推理时间可能过长、满足不了实时要求。
- **推理速度** = 模型处理数据并生成预测的时长。
- 例：**自动驾驶**需即时决策；**KNN（k 最近邻）** 大部分计算在推理阶段做、预测慢，且自动驾驶是**高维问题**，KNN 不合适 → 要按**用例对推理速度的要求**选模型。

#### 4. 模态、多语言、架构与复杂度

- **模态 (Modality)**：每种模态有特定嵌入；**集成方法 (ensemble)** 结合多个模型比单模型性能更好。
- **多语言 (Multilingual)**：需要时选经过相关语言训练的多语言模型。
- **架构**：不同架构各有优劣、适配不同任务（图像识别→CNN；NLP→RNN）。
- **复杂度 (Complexity)**：由参数、层数、操作数衡量；影响速度、内存、准确率。**更复杂 → 通常更准，但更耗算力和数据、更难解释**。

#### 5. 用指标评估/比较模型

- 标准指标：准确率、查准率、查全率、F1、**RMSE**、**平均查准率 (MAP)**、MAE。
- 要看**指标间的权衡**、选**与任务最相关**的指标。例：**对象检测更看 MAP**（衡量定位+分类多个对象的能力）而非准确率。
- **数据不平衡/分布不均时，不建议用准确率**（呼应领域 1）。

> **第 2 课：偏差、可用性/兼容性、自定义与可解释性**

#### 1. 训练数据偏差

- 训练数据可能有**偏差**；要懂得降低风险、解决道德问题，据此做模型选择和微调决策。

#### 2. 可用性与兼容性

- 预训练模型可从 **TensorFlow Hub、PyTorch Hub、Hugging Face** 等仓库找到。
- 选之前检查：是否与你的**框架/语言/环境兼容**、有无**许可证和文档**、是否**定期更新维护**、有无已知问题或限制。

#### 3. 自定义与可解释性（重点）

- 可能需修改/扩展模型（加层、类、特征）；也想理解它**如何做预测** → 找**灵活、模块化、透明**、带可视化/解释工具的模型。
- **可诠释性 (Interpretability)**：能用系数和公式**数学地解释**为何这样预测——**只有足够简单的模型能做到**。
- **基础模型极其复杂 → 天生不透明，是"黑盒 (black box)"**。
- **可解释性 (Explainability)**：用一个**更简单、可解释的模型去局部近似**黑盒，从而解释它——**与可诠释性不同**。
- **若"可诠释性"是硬要求，预训练基础模型可能不是最佳选择**；线性回归、决策树等更易解释。
- 复杂度权衡：更复杂 → 能发现复杂模式、性能可能更高，但**成本更高、更难解释**。还要考虑硬件限制、维护更新、数据隐私、迁移学习。

---

> **第 3 课：推理参数 + 提示词基础 + 向量数据库**

#### 1. 推理参数 (Inference Parameters)

- **推理**：用模型对新数据做预测/生成输出的过程；Amazon Bedrock 让你在所选 FM 上做推理，输入是**提示词**。
- 推理参数 = 一组可调值，用来**限制或影响模型响应**。Bedrock 支持：
  - **控制随机性/多样性**：**温度 (Temperature)、Top K、Top P**。
  - **限制长度**：**响应长度、惩罚 (penalties)、停止序列 (stop sequences)**。
- 要**实验**找到多样性、一致性、资源效率的最佳平衡；上线后**持续监控和调整**。

#### 2. 提示词工程基础

- **提示词 (Prompt)**：用户提供的一组特定输入，指导 LLM 为任务生成合适响应。
- 可加入来自内部数据库/向量数据存储的**上下文数据**丰富提示词 → 即 **RAG**。

#### 3. 向量数据库 (Vector Database)（重点）

- 是**以数学表示（向量）形式存储的数据集合**（类比 Excel），可存结构化和非结构化数据（文本/图像）的**向量嵌入**。
- **嵌入**：把词/句等转成数字，表示含义和关系。
- **ML 模型（尤其嵌入模型）是创建向量数据库的前提**：用嵌入模型把输入数据填充成密集向量。
- 作用：作为基于 FM 应用的**事实参考**，帮模型**检索可信数据**、作为**外部数据源**提升搜索建议和文本生成；还提供高效查询、数据管理、容错、认证、访问控制、查询引擎。
- **Amazon Bedrock 知识库**：把数据源汇成信息存储库，构建利用 **RAG** 的应用。

> **第 4 课：RAG 深入 + 存嵌入的 AWS 服务 + AI 代理**

#### 1. RAG（检索增强生成，Retrieval-Augmented Generation）

- **两个组件**：**检索器 (Retriever)** 搜索知识库 + **生成器 (Generator)** 根据检索到的信息生成输出。
- 作用：让模型获取**训练数据之外、特定领域的最新知识**。
- **工作流程**：提示词 →**查询编码器**编码成嵌入 → 在**向量数据库**搜索相似嵌入 → 检索器取回相似数据 → 与原提示词**组合/扩增** → 发给 LLM 生成补全。
- **核心价值：缓解幻觉**——用外部知识库（向量数据库存大量向量编码的知识文章）补充 LLM，让回答**准确且贴合上下文**。
- **Amazon Bedrock** 提供与自定义知识库集成的 RAG。用于问答系统、对话系统、基于外部知识的内容生成。

#### 2. 存储嵌入的 AWS 服务（考点，务必记全）

- **Amazon OpenSearch Service**：低延迟搜索/聚合、向量存储与处理；支持**语义搜索、RAG、推荐引擎、媒体搜索**。**OpenSearch 无服务器的向量引擎**免管理基础设施。
- **Amazon Aurora**、**Amazon RDS for PostgreSQL（pgvector 扩展）**、**Amazon Neptune**、**Amazon DocumentDB（兼容 MongoDB）**、**Redis**。
- **语义搜索 (Semantic Search)**：用基于语言的嵌入改善检索（对比关键词搜索）；示例用 **BERT** 生成向量、SageMaker 托管、存入 OpenSearch。
- **Amazon Bedrock 知识库**：完全托管 RAG，把 FM 安全连到公司数据，**以嵌入存储、无需反复重训练 FM**。

#### 3. AI 代理 (Agent)（重点）

- **为什么需要**：FM 能理解和回答，但**无法完成现实任务**（订机票、处理采购单）——这些需要**组织特定数据 + 自定义工作流**。
- **Amazon Bedrock 代理**：完全托管的 AI 能力，可**自动分解任务、生成编排逻辑或写自定义代码、安全地通过 API 连数据库、摄取并结构化数据、用上下文扩增**以生成更准响应并完成请求。
- **代理的角色**：编排"提示词补全工作流"以及**用户请求、FM、外部数据源/应用**之间的交互；**自动调用 API 执行操作**，并调用**知识库**补充相关信息。
- 例：建一个代理帮客户预订水肺潜水度假。

**① 基础模型 (FM) 深入**
- **核心特点=适应性**：靠输入提示词就能高准确地做多种任务（NLP、问答、图像分类），区别于只做单一任务的传统 ML。
- **参数爆炸式增长**：BERT(2018, 3.4亿参数) → GPT-4(2023, 万亿级)；2012 年以来所需算力约**每 3.4 个月翻一倍**。
- **用自监督学习 (self-supervised)** 从无标注数据自建标签——区别于传统 ML 的监督/无监督。
- **FM 示例清单（认识名字）**：**Amazon Nova**（Micro/Lite/Pro 理解模型，Canvas/Reel 生成模型）、**Amazon Titan**、**Claude**（Anthropic，Opus/Sonnet/Haiku）、**AI21 Jurassic**、**Cohere**、**Stable Diffusion**（文生图）、**BLOOM**（多语言）、**Llama、Falcon**、**BERT/GPT**。
- **FM 的挑战**：从零构建**昂贵**、需前端集成（提示工程/微调/管道）、**缺乏真正理解上下文**、答案可能**不可靠/有害/错误**、**偏差**。

**② 推理参数深入（高频，务必理解方向）**

以提示 "I hear the hoof beats of ___"，候选 {horses:0.7, zebras:0.2, unicorns:0.1} 为例：

| 参数 | 作用 | 低值效果 | 高值效果 |
|------|------|----------|----------|
| **温度 (Temperature)** | 调整概率分布形状 | 更**确定**、偏高概率词（更可能选 horses）| 更**随机/有创意**、抬高低概率词（更可能选 unicorns）|
| **Top K** | 只考虑最可能的 **K 个**候选 | 池更小、更保守 | 池更大、更多样。如 Top K=2 只看 horses、zebras |
| **Top P** | 只考虑累积概率前 **P%** 的候选 | 池更小 | 池更大。如 Top P=0.7 只看 horses；0.9 看 horses+zebras |

- **长度控制**：**响应长度 (Response length)**（min/max token）、**惩罚 (Penalties)**（对长度/重复/频率/类型惩罚）、**停止序列 (Stop sequences)**（生成到指定字符序列就停）。

**③ 向量数据库深入**
- **语义搜索 (Semantic Search)**：用嵌入按**含义**检索（"a cozy place to sit by the fire" 能找到沙发），比关键词搜索相关性更高。
- **k-NN（k 最近邻）**：算查询向量与库中向量的距离找最相似。数据量大时用 **ANN（近似最近邻）** 提速。
- **ANN 算法**：**HNSW（分层可导航小世界，图结构）** 和 **IVF（倒排文件，分桶）**——大规模用。
- **距离/相似度度量**：欧氏距离、L1(曼哈顿)、L∞(棋盘)、内积 (inner product)、**余弦相似度 (cosine)**、汉明距离。
- **分块 (Chunking)**：把领域数据切成有意义的语义单元（词/句/段/文档）再做嵌入；块大小影响性能、嵌入生成和推理成本。
- **各 AWS 向量库选型**（都可存嵌入）：
  - **Aurora PostgreSQL / RDS for PostgreSQL（pgvector）**：已用关系库/PostgreSQL 时首选。
  - **OpenSearch Service（k-NN 插件）/ OpenSearch 无服务器向量引擎**：需水平扩展、混合搜索（关键词+语义）时。
  - **MemoryDB（Redis 兼容）**：**实时、超低延迟**（个位数毫秒）。
  - **Neptune Analytics**：**GraphRAG**、高度连接的图数据。
  - **DocumentDB（兼容 MongoDB）**：用 MongoDB API 时。
- **嵌入应存在离源数据近的地方**：简化数据管道、便于加元数据、复用访问/安全控制。

**④ Bedrock 知识库（Knowledge Bases）与代理（Agents）**
- **知识库两类**：
  - **托管知识库 (Managed)**：Bedrock 托管摄取/索引/存储/检索，支持多模态、自动扩缩、**智能体检索（多跳推理）**、第三方连接器（S3/SharePoint/Confluence 等）、文档级权限、与 **AgentCore Gateway/MCP** 原生集成、**引用 (citations)** 便于核查。
  - **自管知识库 (Customer-managed)**：自己管 RAG 管道和向量库（OpenSearch Serverless/Aurora/Neptune），完全控制摄取/解析/索引。
- **代理 (Agents)**：编排 FM、数据源、应用、用户对话之间的交互；**自动调 API 执行操作、调知识库补信息**；Bedrock 托管**提示工程、记忆、监控、加密、权限、API 调用**。
  - 配置含 **动作组 (Action Groups)**（定义可执行的操作）+ 关联知识库；可用**追踪 (traces)** 查看推理过程。
  - 注意：**Bedrock Agents Classic 已停止接新客户**，新能力用 **Amazon Bedrock AgentCore**。

### 关键术语速记

> 术语以「中文 (English)」对照。

**选型考量**
- **成本 / 延迟 (Latency) / 推理速度 (Inference Speed) / 模态 (Modality) / 多语言 (Multilingual) / 模型规模 / 复杂度 (Complexity)**。
- **集成方法 (Ensemble)**：结合多个模型，性能优于单模型。
- **KNN（k 最近邻）**：推理阶段计算多、慢；不适合高维实时场景（如自动驾驶）。
- **MAP（平均查准率，Mean Average Precision）**：对象检测常用（定位+分类多对象）。

**可解释性**
- **可诠释性 (Interpretability)**：用数学（系数/公式）解释预测；仅简单模型可行。
- **可解释性 (Explainability)**：用更简单模型**局部近似**黑盒来解释。
- **黑盒 (Black Box)**：极复杂、不透明的模型（如 FM）。

**推理参数**
- **温度 (Temperature) / Top K / Top P**：控制随机性和多样性。
- **响应长度 / 惩罚 (Penalties) / 停止序列 (Stop Sequences)**：限制长度。

**RAG 与向量**
- **RAG（检索增强生成）**：检索器 + 生成器，用外部知识补充 LLM、缓解幻觉。
- **向量数据库 (Vector Database)**：存向量嵌入、供语义检索。
- **嵌入 (Embedding) / 语义搜索 (Semantic Search) / 查询编码器 (Query Encoder)**。
- **Amazon Bedrock 知识库 (Knowledge Bases)**：完全托管 RAG。

**代理**
- **AI 代理 (Agent)**：编排任务、调用 API/知识库、执行多步骤现实任务。
- **Amazon Bedrock 代理 (Bedrock Agents)**。

### 易考点 / 陷阱

- **选模型没有"最好"，只有"最适合需求"**：在成本/延迟/模态/复杂度/可解释性间权衡；准确率高一点点但贵很多不一定值。
- **实时/低延迟场景**（自动驾驶）别选推理慢的模型（如 KNN、超复杂模型）。
- **对象检测看 MAP**、**数据不平衡别用准确率**——按任务选指标。
- **可诠释性 vs 可解释性**：诠释=数学直接解释（简单模型）；解释=用简单模型近似黑盒。**要硬性可诠释 → 别用 FM，用线性回归/决策树**。
- **RAG 的核心价值 = 用外部/最新知识缓解幻觉**，且**无需重训练模型**；流程：编码→向量库检索→扩增提示→生成。
- **存嵌入的 AWS 服务要记全**：OpenSearch、Aurora、RDS for PostgreSQL(pgvector)、Neptune、DocumentDB、Redis。
- **RAG vs 微调**：缺"最新/私有知识"→RAG（不改模型权重）；要"改变模型行为/风格/领域能力"→微调。

### 🌱 一句话入门（零基础先看这里）

**提示词工程 = 学会"好好跟 AI 说话"**——通过精心设计输入提示词，引导模型给出更好的输出。同一个模型，提示写得好不好，结果天差地别。

- **提示词的组成**：**指令/任务 + 上下文 + 输入文本**。
- **常用技术**：零样本（不给例子）、少样本（给几个例子）、思维链（让它分步推理）、提示模板。
- **要懂模型的"潜在空间"**：模型的知识是训练数据里的统计模式。**问它不知道的东西 → 它会挑最接近的答案 → 产生幻觉**。所以提示前先评估"它到底懂不懂这个主题"。

> 一句话：**说清楚（具体）、给例子、让它分步、加护栏**。

### 视频学习笔记

> 本任务共 2 节课。

---

> **第 1 课：提示词的组件、技术与潜在空间**

#### 1. 提示词的组件

- **提示词 (Prompt)**：用户提供的一组特定输入，指导 LLM 为任务生成合适响应。
- 组件（按用例可含一个或多个）：**任务/指令 (Instruction)、上下文 (Context)、输入文本 (Input)**。

#### 2. 提示词技术（重点）

- **零样本提示 (Zero-shot)**：不给任何示例（如情绪分类直接问）。
- **少样本提示 (Few-shot)**：给几个示例，帮模型校准输出以符合期望。
- **提示模板 (Prompt Template)**：包含说明、少样本示例、针对不同用例的具体内容和问题。
- **思维链 (Chain-of-Thought, CoT)**：把推理**分解为多个中间步骤**，提高复杂任务输出的质量和连贯性。
- **提示优化 / 提示微调 (Prompt Tuning)**（高级）：用训练中优化的**连续嵌入**替代实际提示文本；**冻结其余模型参数**，比完全微调更高效。

#### 3. 提示词工程的定义

- AWS 定义：**编写和优化输入提示词**的实践——选用合适的词、短语、句子、标点、分隔符，有效地把 LLM 用于各种应用。
- **提示词质量 → 直接影响响应质量**。
- Bedrock 上 LLM 支持的常见任务：分类、有/无上下文问答、摘要、开放式文本生成、代码生成、数学、推理/逻辑。

#### 4. 潜在空间 (Latent Space)（关键概念）

- 定义：**LLM 中编码的语言知识**——存储的数据模式，捕获关系，出现提示时据此重构语言。
- 类比：潜水度假模型把目的地/深度/能见度/水温等训练成一个"统计数据库"；用户问"哪里能浮潜看海牛"，模型查这个目录给建议——**这个统计数据库就是潜在空间**。

---

> **第 2 课：潜在空间的局限、最佳实践、风险与防护**

#### 1. 潜在空间与幻觉

- 所有语言模型基于大型文本库训练（RefinedWeb、Common Crawl、StarCoder、BookCorpus、Wikipedia、C4 等），知识**质量参差不齐**（出现在维基百科不代表正确）。
- 提示被模型摄取 → 参考潜在空间 → 返回统计数据组合成词。
- **得到差/负面响应的两种原因**：①提示写得不够好；②**模型潜在空间里没有该主题的足够信息**（尤其小模型）→ 模型选**最接近的匹配**→ 产生**幻觉**（看似正确，实为编造）。
- **模型不会推理**：它一次一个词、按**条件概率**从库里选词（问"恐龙时代第一个潜到25英尺以下的人是谁"，它不会像人一样推理出"那时没人潜水"）。
- **高级提示词工程的关键**：先**评估某主题的潜在空间**（模型到底懂多少），别拿它几乎不懂的主题去问，否则大概率是幻觉。

#### 2. 提示词工程最佳实践（7 条，考点）

1. **具体明确的说明**：格式、示例、对比、风格、语气、输出长度、详细上下文。
2. **提供示例**：示例文本、数据格式、模板、代码、图表等。
3. **迭代实验**：测试提示、观察修改如何改变响应。
4. **了解模型优缺点**。
5. **平衡简单与复杂**：避免模糊、无关、意外的答案。
6. **使用多个注释 (multiple comments/annotations)** 提供更多上下文，让提示更相关。
7. **添加防护机制 (Guardrails)**。

#### 3. 提示词工程的风险（重点，易混，务必分清）

- **提示词注入 (Prompt Injection)**：提示**操纵攻击**——可信提示（开发者写的）与**用户的不可信输入**并存，诱导生成恶意/不想要的响应。
- **越狱 / 破解 (Jailbreaking)**：试图**绕过你建立的防护机制/安全措施**。
- **劫持 (Hijacking)**：用**新指令更改或操纵原始提示**。
- **投毒 (Poisoning)**：在消息、邮件、网页等中**嵌入有害指令**。
- **暴露 (Exposure)**：敏感信息泄露风险。

#### 4. 防护机制 (Guardrails)

- 提供**安全和隐私控制**来管理 GenAI 应用中的交互：
  - 定义应用中**不可取的主题**；
  - 设置**要屏蔽的词**；
  - 配置**阈值**过滤有害类别和**提示词攻击**（越狱、提示词注入）；
  - 过滤可能含**敏感数据**的输入。
- AWS：**Amazon Bedrock + Amazon Titan** 提供预训练模型，可用提示词工程自定义/控制，并提供构建/优化提示、监控分析输出的 API 和工具。

#### 📎 补充资料（额外阅读）：提示词技术分类学 + 最佳实践

> 来源：AWS "What is prompt engineering" 整理。基础级考试**认识名字和用途**即可，不用死记每种。

**进阶提示技术（了解思路）**
- **思维链 (Chain-of-Thought, CoT)**：把复杂问题拆成一串**中间推理步骤**；可多次"rollout"取**最常达成的结论**。
- **思维树 (Tree-of-Thought, ToT)**：CoT 的推广——生成**多个可能的下一步**，用**树搜索**探索。
- **诘问式 (Maieutic) 提示**：让模型给答案+解释，再解释解释的各部分，**剪掉不一致的解释树**，改善常识推理。
- **基于复杂度 (Complexity-based)**：跑多个 CoT，选**推理链最长**且结论最常见的。
- **生成知识 (Generated Knowledge)**：先让模型**生成相关事实**，再据此完成任务，提升质量。
- **由少到多 (Least-to-most)**：先列子问题，再**按序求解**（后面的用前面的答案）。
- **自我修正 (Self-refine)**：模型**解题→自我批评→再改**，循环到满足停止条件。
- **定向刺激 (Directional-stimulus)**：给**关键词提示/线索**引导输出（如要求诗里含"heart, passion, eternal"）。

**最佳实践（4 条精炼版）**
1. **提示无歧义 (Unambiguous)**：明确要"摘要"还是"详细分析"。
2. **提供充分上下文 + 输出要求**：如"列 1990 年代最流行电影，用表格，列 N 部"。
3. **平衡"目标信息"与"输出"**：太简单缺上下文、太复杂让模型困惑；用简单语言、缩短提示。
4. **实验并迭代 (Experiment & refine)**：反复测试、观察修改如何改变输出。

**提示工程的价值**：更强的开发者控制、更好的用户体验、更高的灵活性（可复用领域中立的提示模板、规模化）。

### ⚠️ 视频未覆盖 / 需补充（对照考纲）

- **负面提示 (Negative Prompting)**：明确告诉模型**不要**做什么/不要包含什么（常见于图像生成，如"不要出现文字/水印"；文本里如"不要用专业术语"）。是提示词的构成要素之一。
- **Amazon Bedrock Prompt Management**：Bedrock 的功能，用于**创建、存储、版本控制和管理提示词**——把提示当作可复用、可迭代、可协作的资产（类似给提示词做"版本管理"），便于团队在不同模型/版本间测试和部署最优提示。

### 关键术语速记

> 术语以「中文 (English)」对照。

**提示词构成与技术**
- **提示词 (Prompt)** = 指令/任务 (Instruction) + 上下文 (Context) + 输入 (Input)。
- **零样本 (Zero-shot) / 少样本 (Few-shot) / 单样本 (One-shot)**：给 0 / 几个 / 1 个示例。

**核心概念**
- **提示词工程 (Prompt Engineering)**：编写和优化输入提示的实践；质量决定响应质量。
- **潜在空间 (Latent Space)**：LLM 编码的语言知识（统计模式库）；缺相关知识 → 幻觉。

### 易考点 / 陷阱

- **提示词组件**：指令 + 上下文 + 输入；**零/单/少样本**看给的示例数（0/1/几个）。

  - **投毒**=在内容里埋有害指令。
- **防护机制 (Guardrails)** 是应对这些风险的手段（屏蔽/过滤/拦截）；对应 **Amazon Bedrock Guardrails**。
- **负面提示**=告诉模型"不要做什么"（补考纲）。
- **提示词版本管理** → **Amazon Bedrock Prompt Management**（补考纲）。

## 任务说明 3.3：描述基础模型的训练和微调过程

**官方目标：**
- 描述训练基础模型的关键要素（预训练、微调、持续预训练、蒸馏）
- 定义微调基础模型的方法（指令优化、针对特定领域调整模型、迁移学习、持续预训练）
- 描述如何准备数据以微调 FM（数据策管、监管、调整大小、标记、代表性、人类反馈强化学习 [RLHF]）

### 🌱 一句话入门（零基础先看这里）

这个任务讲**基础模型是怎么"练出来"和"调优"的**，以及**微调前怎么准备数据**。

- **三种训练要素**：**预训练**（从零学语言，超贵超慢）、**微调**（在预训练模型上用你的数据再训练、改权重）、**持续预训练**（不断喂新数据让模型越来越强）。
- **微调的坑**：只练一个任务可能导致**灾难性遗忘**（学会新任务、忘了旧本领）→ 用**多任务微调**或 **PEFT**（只调一小部分参数）缓解。
- **准备数据**：收集→预处理→拆分（训练/验证/测试）→标注/去偏差，AWS 有一整套工具。

> 记住成本梯度：**预训练最贵 > 全量微调 > PEFT/LoRA（高效）> RAG/提示词（最便宜，不改权重）**。

### 视频学习笔记

> 本任务共 2 节课。

---

> **第 1 课：训练要素、微调方法、灾难性遗忘、PEFT/LoRA**

#### 1. 训练 FM 的三个关键要素

- **预训练 (Pre-training)**：用**大量非结构化数据 + 自监督学习**训练 LLM，学会语言基础功能。极其昂贵：需**数百万 GPU、大量算力时间、TB/PB 级数据、数万亿 Token、反复试错**。
- **微调 (Fine-tuning)**：在预训练模型上**扩展训练**、针对特定任务改善输出；是**有监督学习**，用**标注示例**更新 LLM 权重，让 FM 适配你的自定义数据和用例。
- **持续预训练 (Continued Pre-training)**：不断用不同主题/类型/背景的数据预训练，模型随时间变强，更会处理**域外数据**。

#### 2. 预训练 vs 微调

- 预训练：**无标注**数据、自监督、学语言基础。
- 微调：**有标注**示例、有监督、适配领域/任务。

#### 3. 微调的方法

- **基于指令的微调 (Instruction Fine-tuning)**：用标注示例改进**特定任务**性能。
- **领域自适应微调 (Domain Adaptation)**：用**有限的领域特定数据**调整模型，让它掌握**行话、技术术语、专业数据**。（Amazon SageMaker JumpStart 支持对领域特定数据集的文本生成模型做微调。）
- **多任务微调 (Multi-task Fine-tuning)**：训练集含**多个任务**的输入输出示例（评分、摘要、翻译、代码等）→ 得到**指令优化模型**，能同时做多任务；**需大量数据**；可缓解灾难性遗忘。
- **RLHF（基于人类反馈的强化学习）**：用人类反馈数据微调，让模型更懂类人提示、生成类人响应、**对齐人类偏好**。

#### 4. 灾难性遗忘 (Catastrophic Forgetting)（重点）

- **定义**：全量微调修改了原始 LLM 的**所有权重** → 提升了单任务性能，但**降低了模型执行其他任务的能力**（学了新的、忘了旧的）。
- **是否在意**：若只需模型稳定做**单一任务**，可能不在乎它对其他任务的影响。
- **缓解**：**多任务微调**（计算多任务损失更新权重）、**PEFT**。

#### 5. 参数高效微调 (PEFT) 与 LoRA（重点）

- **全量微调 (Full Fine-tuning)**：更新**每个参数**；加载参数 + 优化器/梯度/激活等占用大量 GPU 内存，计算成本高。
- **PEFT（参数高效微调，Parameter-Efficient Fine-tuning）**：**冻结原始 LLM 大部分参数/权重**，只微调**少量任务特定的适配层和参数** → 大幅减少所需算力和内存。
- **LoRA（低秩自适应，Low-Rank Adaptation）**：流行的 PEFT 技术；冻结原始权重，在 **Transformer 每层创建新的可训练低秩矩阵**。
- **PEFT/LoRA 修改权重、但不修改"表征 (representation)"**（表征编码语义信息、类似嵌入）。
- **ReFT（表征微调，Representation Fine-tuning）**：冻结基础模型，学习针对**隐藏表征**的任务特定干预；基于"线性表征假说"（概念编码在神经网络的线性表征子空间）。

---

> **第 2 课：准备微调数据 + AWS 数据准备工具 + 持续预训练**

#### 1. 微调数据准备流程

- 用公开数据集和**提示词模板库**（含多任务/多数据集的模板）准备**指令数据集**。
- **拆分**：训练 / 验证 / 测试。
- **微调循环**：从训练集选提示 → LLM 生成补全 → 把补全分布与**训练标签**比较算**损失** → 用损失**更新权重**；多批"提示-补全对"后性能提升。
- **评估**：用**留出验证集 (holdout validation)** 衡量性能得**验证准确率**；微调完用**留出测试集**做最终评估得**测试准确率**。

#### 2. AWS 数据准备工具（按需求选，考点）

#### 3. 持续预训练 (Continued Pre-training) 的价值

- GenAI 输出**不确定**，验证更难 → 要选合适的**指标、基准、数据集**评估能力、确保不产生有害输出。
- 不断用新数据预训练 → 模型积累更广知识、更强适应性、更会用域外数据 → 为组织创造价值。
- **Amazon Bedrock 持续预训练**：可用**自己的未标注数据**在安全托管环境自定义 **Amazon Titan Text** 等 FM。

#### 📎 补充资料（额外阅读）：领域自适应微调实例 + 困惑度 (PPL)

> 来源：AWS "Domain-adaptation Fine-tuning of FMs in SageMaker JumpStart on Financial data" 整理。

**领域自适应微调实例（金融）**
- 用 **SageMaker JumpStart** 对 **GPT-J 6B** 用**金融 SEC 文件**做微调（微调=迁移学习：把一个任务学到的知识迁到相关任务）。
- 效果对比"什么驱动 Amazon 销售增长？"：
  - 微调前：泛泛而谈、答非所问。
  - 微调后：能答"主要由客户使用增加、选择更多、价格更低、便利性提升、第三方卖家销售增长驱动"——**明显更专业准确**。
- **零样本问答**也显著变好。

**困惑度 (Perplexity, PPL)——评估语言模型的指标**
- 衡量模型**预测序列下一个词**的能力；**PPL 越低越好**（预测越准）。
- 可用于**比较不同模型**或**跟踪同一模型随时间的表现**。
- 实例：微调前 PPL=8.147 → 微调后 PPL=1.437（大幅下降=变好）。

**关键超参数（了解即可）**
- **epochs**（训练轮数）、**learning_rate**（学习率/步长）、**weight_decay**（正则化强度，防过拟合）、**fp16**（16 位混合精度，省内存）、**eval_steps**（多少步在验证集评估一次）、**gradient_accumulation_steps**（累积梯度步数）。
- JumpStart 用 **Hugging Face DLC + DeepSpeed**（减少算力/内存、支持单实例多 GPU 分布式训练）。

### 关键术语速记

> 术语以「中文 (English)」对照。

**训练要素**
- **预训练 (Pre-training)**：无标注 + 自监督，学语言基础；最贵。
- **微调 (Fine-tuning)**：有标注 + 有监督，改权重适配领域/任务。
- **持续预训练 (Continued Pre-training)**：不断喂新数据，用未标注数据增强。

**微调方法**
- **指令微调 (Instruction Fine-tuning)**：标注示例改进特定任务。
- **领域自适应微调 (Domain Adaptation)**：少量领域数据学行话/术语。
- **多任务微调 (Multi-task Fine-tuning)**：多任务示例→指令优化模型；缓解遗忘；需大量数据。
- **RLHF（基于人类反馈的强化学习）**：对齐人类偏好。

**高效微调**
- **灾难性遗忘 (Catastrophic Forgetting)**：全量微调改所有权重，损害其他任务能力。
- **全量微调 (Full Fine-tuning)**：更新所有参数，成本高。
- **PEFT（参数高效微调）**：冻结多数参数、只调少量适配层，省算力内存。
- **LoRA（低秩自适应）**：PEFT 技术，在 Transformer 每层加可训练低秩矩阵；不改表征。
- **ReFT（表征微调）**：干预隐藏表征。
- **表征 (Representation)**：编码语义信息，类似嵌入。

**数据准备**
- **训练/验证/测试拆分、损失 (Loss)、留出验证/测试集、验证/测试准确率**。

**AWS 工具**
- **SageMaker Canvas / EMR / Glue / Feature Store / Clarify / Ground Truth / JumpStart**。
- **Amazon Bedrock 持续预训练（Titan Text）**。

### 易考点 / 陷阱

- **预训练 vs 微调**：预训练=无标注+自监督+学语言基础（最贵）；微调=有标注+有监督+改权重适配任务。
- **成本梯度**（高频权衡题，也见 3.1）：**预训练 > 全量微调 > PEFT/LoRA > RAG/提示词工程**。要省钱优先提示词/RAG，不改权重。
- **灾难性遗忘**：全量单任务微调会损害其他任务能力；**多任务微调**和 **PEFT** 可缓解。
- **PEFT/LoRA**：冻结大部分参数、只调少量 → 省算力内存；**LoRA 在每层加低秩矩阵**、不改表征。
- **微调方法对号入座**：改进特定任务→指令微调；学行话/领域术语→领域自适应；同时会多任务→多任务微调；对齐人类偏好→RLHF。
- **数据准备工具对号入座**（易考）：低代码→Canvas；检测偏差→Clarify；标注→Ground Truth；特征→Feature Store；无服务器→Glue；大规模→EMR。
- **数据拆分**：训练/验证/测试；验证集调优、测试集做最终评估。
- **持续预训练**用**未标注**数据（对比微调用标注数据）；Bedrock 可对 Titan 做持续预训练。

## 任务说明 3.4：描述评估基础模型性能的方法

**官方目标：**
- 确定评估 FM 性能的方法（人工参与评估、基准数据集、Amazon Bedrock 模型评估）
- 识别评估 FM 性能的相关指标（ROUGE、BLEU、BERTScore、LLM 评审员）
- 确定 FM 能否有效满足业务目标（生产力、用户参与度、任务工程）
- 确定评估使用 FM 构建的应用程序性能的方法（RAG、代理、工作流）
- 确定 AI 应用程序的业务目标一致性指标（任务完成率、用户满意度、每次交互成本）

### 🌱 一句话入门（零基础先看这里）

这个任务讲**怎么判断一个基础模型/GenAI 应用"好不好用、值不值"**，以及**部署集成时要考虑什么**。

- **为什么难评估**：传统 ML 输出确定（可直接和标签比、算准确率）；**GenAI 输出不确定**，所以要用**任务特定的指标**。
- **常用指标**：**ROUGE（摘要）、BLEU（翻译）、BERTScore（语义相似度/查幻觉）**；还有 **LLM 评审员**、人工评估。
- **通用基准**：GLUE/SuperGLUE、MMLU、BIG-Bench、HELM——比较无特定任务的通用模型。
- **业务对齐**：最终要看是否达成业务目标（任务完成率、用户满意度、每次交互成本）。

> 记忆：**ROUGE=摘要、BLEU=翻译、BERTScore=语义相似/查幻觉**；通用比较用**基准 (benchmark)**；最终看**业务指标**。

### 视频学习笔记

> 本任务共 2 节课。

---

> **第 1 课：部署优化 + 评估指标与基准**

#### 1. 部署时要问的问题（第一组：模型如何运行）

- 期望生成速度多快？计算预算多少？**愿不愿意牺牲性能换推理速度/更小存储？**
- 本地/云/边缘部署都可能有**算力、存储、低延迟**挑战。

#### 2. 优化技术（性能 vs 准确率的权衡）

- **减小模型 (model size)**：模型越小加载越快、推理延迟越低，但**可能降低性能**。
- 其他：**更简洁的提示词**、**减小检索片段的大小和数量**、用**推理参数和提示**减少生成量。
- 生成模型上有些技术更有效，但常需在**准确率和性能之间权衡**。

#### 3. 为什么 GenAI 评估更难

- 传统 ML：预测**确定性**，可与标签比，**准确率/RMSE 好算**。
- GenAI：输出**不确定** → 评估更难确定，**指标更特定于任务**。

#### 4. 核心评估指标（重点，务必分清）

- **ROUGE（Recall-Oriented Understudy for Gisting Evaluation）**：评估**自动摘要**（也用于机器翻译）；比较输入与生成输出的质量。
- **BLEU（Bilingual Evaluation Understudy）**：评估**机器翻译**质量（一种语言→另一种）。
- **BERTScore**：基于人类参考自动比较，算**语义相似度**；适合评估文本生成的**忠实度和幻觉**。

#### 5. 通用基准与数据集（比较无特定任务的 LLM）

- **GLUE（通用语言理解评估）**：一组 NLP 任务（情绪分析、问答）；帮开发广泛适用的模型；有排行榜。**SuperGLUE**（2019）加了多句推理、阅读理解等更难任务。
- **MMLU（大规模多任务语言理解）**：评估模型的**知识和问题解决能力**（历史、数学、法律、计算机等）。
- **BIG-Bench（超越模仿游戏基准）**：侧重当前模型**难以完成**的任务（数学、生物、物理、偏差、语言学、推理、儿童发展、软件开发等）。
- **HELM（整体语言模型评估）**：提升**模型透明度**，指导"哪个模型擅长哪个任务"；是摘要、问答、情绪分析、偏差检测等任务指标的组合。

#### 6. 人工与 AWS 评估工具

- **人工评估**：人工手动比较模型响应（如比较 SageMaker JumpStart 模型或非 AWS 模型的响应）。
- **Amazon SageMaker Clarify**：可评估 LLM、创建模型评估任务，比较 JumpStart 文本 FM 的质量和指标。
- **Amazon Bedrock 评估模块**：自动比较生成的响应、基于人类参考算 **BERTScore**，评估文本生成的**忠实度和幻觉**。

---

> **第 2 课：集成到应用（RAG、编排、端到端堆栈、业务对齐）**

#### 1. 第二组问题：如何把模型集成到应用

- 模型需要哪些额外资源？是否要与**外部数据/其他应用**交互？如何连接？

#### 2. RAG 再强调（解决什么）

- **知识过时**：模型不知道较新信息 → RAG 在**推理时访问外部数据**，无需反复重训练（重训练成本高）。
- **复杂数学**：模型可能给接近但不正确的答案。
- **幻觉**：RAG 提供上下文、**建立响应的事实依据 (grounding)**，提升真实性。
- 需要**编排库 (orchestration library)** 来管理用户输入传入 LLM、补全返回的流程。

#### 3. 判断 FM 是否达成业务目标

- 用 FM/LLM 实现业务目标、增强用户体验；用评估技术确认目标是否达成。
- 步骤：**先按要解决的具体问题设定业务目标 → 确定成功指标和支撑基础设施 → 衡量、监控、审查指标评估性能。**
- 目标示例：**生产力、用户参与度 (user engagement)、任务工程**。
- 业务对齐指标：**任务完成率、用户满意度、每次交互成本 (cost per interaction)**。

#### 4. 端到端解决方案的关键层

- **基础设施层**：计算/存储/网络，托管 LLM 和应用组件；**全生命周期安全处理数据**（准备/训练/推理）。
- **模型层**：选 LLM + 合适的推理基础设施；加**额外存储**（存用户补全/反馈用于后续微调/评估/对齐）；决定实时 vs 近实时交互；加安全隔离数据。
- **工具/框架层**：额外的 LLM 工具与框架、**模型中心 (model hub)** 集中管理和共享模型。
- **应用/接口层**：用户界面（网站/REST API）；重点是**安全连接**；用户（人或其他系统via API）与整个堆栈交互。

### ⚠️ 视频未覆盖 / 需补充（对照考纲）

- **LLM 评审员（LLM-as-a-judge）**：用**另一个（通常更强的）LLM** 来自动给模型输出打分/评判质量——是介于"纯自动指标"和"人工评估"之间的方法，可扩展、成本低于纯人工。考纲把它与 ROUGE/BLEU/BERTScore 并列为 FM 评估指标/方法。
- **评估用 FM 构建的应用（而非只评估模型）**：对 **RAG、代理、工作流** 这类由多组件构成的应用，要**端到端评估**（如检索是否相关、代理是否完成任务、整体任务完成率），而不只看模型单点输出。

### 易考点 / 陷阱

- **三大指标对号入座（最高频）**：**ROUGE=摘要**、**BLEU=翻译**、**BERTScore=语义相似度/查幻觉**——别搞混（延续 2.2）。
- **GenAI 难评估的根因**：输出**不确定**，不能像传统 ML 那样直接算准确率。
- **通用基准别混**：GLUE/SuperGLUE=通用 NLP 任务；MMLU=多学科知识；BIG-Bench=难任务；HELM=透明度+多指标组合。
- **BERTScore 对应 Amazon Bedrock 评估模块**，用于查**忠实度和幻觉**。
- **RAG 解决三件事**：知识过时、（部分）复杂计算、幻觉（提供 grounding）；**无需反复重训练**。
- **评估应用 vs 评估模型**：RAG/代理/工作流要**端到端评估**（补考纲）。
- **业务对齐指标**：任务完成率、用户满意度、每次交互成本——区别于技术指标（ROUGE/BLEU）。
- **优化权衡**：减小模型/简化提示/减少检索片段能降延迟，但可能牺牲准确率。
- **LLM 评审员**：用 LLM 当"裁判"给输出打分（补考纲）。

### 🎴 闪卡 Q&A（遮住答案自测）

<details><summary>1. 为什么 GenAI 比传统 ML 更难评估？</summary>
传统 ML 输出确定、可与标签比、算准确率/RMSE；GenAI 输出不确定，需要任务特定的指标（如 ROUGE/BLEU/BERTScore）。</details>

<details><summary>2. ROUGE、BLEU、BERTScore 分别评估什么？</summary>
ROUGE=摘要（也用于翻译）；BLEU=机器翻译；BERTScore=语义相似度，评估忠实度/幻觉。</details>

<details><summary>3. GLUE、MMLU、BIG-Bench、HELM 各侧重什么？</summary>
GLUE/SuperGLUE=通用 NLP 任务集；MMLU=多学科知识+解题；BIG-Bench=当前模型难完成的任务；HELM=提升透明度、多任务指标组合。</details>

<details><summary>4. AWS 里用哪个服务算 BERTScore 评估忠实度/幻觉？</summary>
Amazon Bedrock 的评估模块（基于人类参考自动比较、算语义相似度 BERTScore）。</details>

<details><summary>5. RAG 帮助解决哪些问题？</summary>
知识过时（推理时取外部数据、免反复重训练）、部分复杂计算、幻觉（提供上下文/事实依据 grounding 提升真实性）。</details>

<details><summary>6. 什么是 LLM 评审员 (LLM-as-a-judge)？</summary>
用另一个（通常更强的）LLM 自动给模型输出打分/评判质量，介于纯自动指标和人工评估之间，可扩展、比纯人工便宜。</details>

<details><summary>7. 评估一个 RAG/代理应用，和评估单个模型有什么不同？</summary>
应用由多组件构成，要端到端评估（检索是否相关、代理是否完成任务、整体任务完成率），而非只看模型单点输出。</details>

<details><summary>8. 衡量 GenAI 应用是否达成业务目标，常用哪些指标？</summary>
任务完成率、用户满意度、每次交互成本，以及生产力、用户参与度。</details>

<details><summary>9. 减小模型能带来什么好处和代价？</summary>
好处：加载更快、推理延迟更低、存储更省；代价：可能降低性能/准确率。</details>

<details><summary>10. 判断 FM 是否达成业务目标的步骤？</summary>
先按具体问题设定业务目标→确定成功指标和支撑基础设施→持续衡量、监控、审查指标评估性能。</details>
